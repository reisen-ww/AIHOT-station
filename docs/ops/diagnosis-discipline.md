# 诊断纪律与假信号清单

站群运维里最贵的错误不是"没修好"，而是**根据假信号改坏了好东西**。这份文档记录已踩过的坑和对应的判断规则。

## 一、判断前先问：这个信号本身可信吗

### 1. 健康检查不要用 `Invoke-RestMethod`

2026-10-22 16:26，四个站点的健康检查全部超时，看起来像全站宕机。实际情况：

- 10 个端口全部 `LISTENING`
- 35 个 node 进程全部存活
- 换成 `curl.exe` 重测：aihot 4.4s → 0.55s → 0.46s、finhot 8.6s、acadhot 4.5s、openhot 5.3s，全部 `ok=true db=ok`

根因：`Invoke-RestMethod` 用的是 .NET 的连接池，在模型接口劣化期间被拖垮，**是检查工具坏了，不是站点坏了**。

```powershell
# 用这个
curl.exe -s -m 10 -o NUL -w "%{http_code} %{time_total}s`n" http://127.0.0.1:3000/api/health

# 不要用这个做健康检查
Invoke-RestMethod http://127.0.0.1:3000/api/health
```

### 2. `receipts.status` 没有 `ok`

统计付费请求前先 `SELECT DISTINCT status`。实际取值是 `completed / failed / received / unknown`。**写 `WHERE status = 'ok'` 会得到恒为 0 的结果**，然后据此得出"模型一次都没成功"的错误结论。

### 3. 表字段要先确认归属

- `title_zh` 在 `analyses` 表，**不在** `articles` 表
- 统计发表数量要用子查询关联 `p.article_id`，直接数 `publications` 会算错

## 二、"坏了"之前，先排除这三种假象

### 假象 1：旧伤

`fail_count` 和 `degraded` 状态会一直保留到下一次成功抓取才清零。**刚恢复时看到一片 degraded 是正常的**。

判断是否真的坏了，看 `last_ok_at` 是否还在推进，不看计数。

```
last_ok_at 在动 → 活着
last_ok_at 停滞 N 小时 + fail_count 持续上涨 → 真的坏了
```

### 假象 2：批次效应

2026-10-21 14:00 AcadHot 均分从 45.1 掉到 28.9，像模型漂移。实际是**当批 25 篇里有 12 篇来自同一个低质源（该源平均分 24.7）**——是样本构成变了，不是模型变了。

判断方法：按源分组看当批均分。单个源拉低整体 vs 所有源同时下降，是两个完全不同的结论。

### 假象 3：反爬拦截

2026-10-21 `fin-fed-press` 报 HTTP 404，像信源死了。实测：直连 200、20 次探测全 200、条件请求返回 304 → **URL 没变、代码没变，是代理抖动期间的首次瞬时错误**。

境外站点 403 集中出现（Import AI / CryptoSlate / Crypto Briefing / Endpoints News / SEC EDGAR 的非浏览器 UA）属于**站点反爬策略**，不是我们的 bug。这类要统一 UA + 降频处理，不要逐个修。

## 三、只有局部数据时，不要下趋势结论

2026-10-22 16:45，依据 40 分钟内 4 个探测点（115s → 130s）判断"模型崩溃式劣化、建议立刻切站"。

拉全天 59 次探测后的事实：`up=54 / DOWN=5`，成功率 91.5%，**5 次 DOWN 全部在下一轮恢复，从未连续两次**，而切档门槛正是连续两次。17:02 延迟回落到 14 秒。

**这是上游间歇抖动，不是劣化。** 若按局部数据切站，会白白重启四站。

规则：

- 判断"恶化"要拉**全天样本**，并看**连续失败次数**（而不是单点最大值）
- 判断"恢复了"同样要看持续性，单点回光返照不算
- 报告里必须写明样本量和时间窗

## 四、多站同时报同一个错 = 找共享前提

2026-10-23 09:59–11:25，四个站的所有信源 `last_error` 全部是 `ECONNREFUSED 127.0.0.1:7897`。

这不是四个站各自坏了，是**代理这个单点挂了**。四站同时出现同一个错误码时，先查共享依赖（代理、数据库、磁盘、模型网关），不要逐站排查。

同理，2026-10-21 的代理故障根因也不是"网络不好"，而是 mihomo 的 DoH 域名被污染到 `127.0.0.1`，导致自己连自己：

```
[DNS] cache hit doh.dns.sb --> [127.0.0.1]
```

修法是两件事都要做：**重启内核**（清连接）+ **等毒化缓存的 TTL 到期**（12:25:34 之后才真正恢复）。

## 五、进程重启才算生效

改了 `.env` 不等于新配置生效。**没有重启的进程仍然跑着旧配置。**

核对当前实际使用的模型/配置，要读运行痕迹（回执里的模型名、接口返回的实际值），不要读配置文件内容。

`.env` 的 mtime 只能证明"文件被改过"，不能证明"进程用了新值"。

## 六、区分设计行为与故障

| 看到的现象 | 是不是故障 | 依据 |
|---|---|---|
| 40% 文章没有分数 | 否 | `relevance='block'` + 预筛 BLOCK，设计内 |
| 日志里只有单档探测 | 否 | 探测从最优档往下、遇 ok 即停 |
| `reports.compose` 反复失败 | 否（噪音） | 重试的是已过去的历史空日报，当天日报不受影响 |
| 一堆 job `fail` 但业务正常 | 视情况 | 按 job 名分类：历史补偿类失败可挂账，当日关键任务失败要查 |
| 采集量远大于分析量 | 否 | 管线按日推进，当天新抓的排在后面 |

**判据：失败条目指向的日期是不是已过去的日子、状态是不是设计内的终态。** 指向历史且内容为空的，是噪音。

## 七、报数字之前的最小核对清单

- [ ] 健康检查用的是 `curl.exe`
- [ ] 统计前 `SELECT DISTINCT status` 确认真实取值
- [ ] 字段归属确认过（`title_zh` 在 `analyses`）
- [ ] 时间窗和样本量写进了结论
- [ ] 区分了"配置意图"和"运行实际"
- [ ] 多站同时报错时，先查共享依赖

缺任何一项，结论都要标注为"未验证"。
