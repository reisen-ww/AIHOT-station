# 断网补偿验收方法论

采集依赖代理出网。代理一挂，四个站会同时报错、同时断粮。这份文档记录**怎么证明"断网期间的内容有没有丢"**——因为直觉判断在这件事上会得出错误结论。

> 2026-10-23 实测：代理断开 1.5 小时（09:59–11:25），断档期发布 201 篇全部入库、全部完成分析，未发现永久丢失。

## 三层结论，强度不同

| 结论 | 证据 | 强度 |
|---|---|---|
| 恢复后系统自动补抓 | 恢复瞬间的入库脉冲 + 之后无新报错 | 强 |
| 库里有记录的断档期文章，全部拿到并分析完 | 按 `published_at` 落在断档窗口内统计，逐条 JOIN `analyses` | 强 |
| 源头发过的文章一篇没漏 | 只有对每个源单独核对 feed 窗口才成立 | **有条件** |

第三层不能靠数据库自证：`published_at` 只能查到"库里已有的文章"，**源头发过但从未进入任何一次 feed 的内容，数据库根本不知道它存在过**。要说"零丢失"，必须去源头数。

## 核心机制：RSS 滚动窗口

每个信源每次只提供最近 N 条（实测 20–30 条）。系统 10 分钟抓一次，恢复后第一次抓取就能把窗口里断档期的内容全部取回。

**补偿能力的上限 = 断档期该源发布的条数 vs 该源 feed 窗口大小：**

- 断档期发布量 ≤ 窗口 → **数学上不可能漏**
- 断档期发布量 > 窗口 → 超出的部分永久丢失，这是 RSS 协议的物理上限，不是系统缺陷

判定公式：`断档期该源发布数 > feed 窗口条数` 就存在理论缺口，缺口上限 = `发布数 − 窗口条数`。

## 正确证据：恢复后首次抓取的 `new_count`

**错误方法**：事后拉当前 feed，看"最老条目是否早于断档起点"。

这个判据会误判。feed 是滚动窗口，断档 3.5 小时后再看，最老条目早就滚过断档起点了——实测钛媒体最老已滚到 11:03、Seeking Alpha 滚到 12:47，都越过了 09:59。按这个判据会把正常恢复冤枉成"漏抓"。

**正确方法**：查恢复后第一次抓取时，系统自己算出的新增条数。`new_count` 的含义是"这条我库里没有"，由系统判定而非人工推断。

```
对每个源：恢复后首抓的 new_count >= 断档期该源发布数 ?
  是 → 窗口内的全拿到了
  否 → 说明恢复时窗口里混有旧条目，需要继续核对
```

## 验收步骤

```sql
-- 1) 断档窗口内发布的文章数（按站统计）
SELECT source_id, count(*) AS published_in_gap
FROM articles
WHERE published_at >= '2026-10-23 09:59' AND published_at < '2026-10-23 11:25'
GROUP BY source_id ORDER BY 2 DESC;

-- 2) 这些文章是否都跑完分析（blocked 是正常拦截，不是失败）
SELECT a.processing_state, count(*)
FROM articles a
WHERE a.published_at >= '2026-10-23 09:59' AND a.published_at < '2026-10-23 11:25'
GROUP BY 1;

-- 3) 恢复瞬间的补抓脉冲（按 10 分钟分桶看入库量突增）
SELECT date_trunc('minute', created_at) - (extract(minute from created_at)::int % 10) * interval '1 minute' AS bucket,
       count(*)
FROM articles WHERE created_at >= '2026-10-23 11:20' AND created_at < '2026-10-23 12:10'
GROUP BY 1 ORDER BY 1;
```

再对发布量最大的 3–4 个源，查恢复后首抓的 `found_count` / `new_count`，与各自 feed 窗口比较。

## 判断"断档期有多长"要用 last_error 的起止

```sql
-- 各站最后一次成功抓取 / 第一次恢复
SELECT station, max(last_ok_at), min(last_error_at)
FROM ... -- 按 sources 表的 health 字段
```

四站同时出现同一个错误码（如 `ECONNREFUSED 127.0.0.1:7897`）= 代理单点故障，不是站点问题；四站的窗口边界应当几乎一致，不一致说明另有原因。

## 三个容易误判的点

### 1. 恢复初期的 `degraded` 计数是旧伤，不是新故障

`fail_count` 会一直保留到下一次成功抓取才清零。刚恢复时看到一片 degraded 属正常，**要看 `last_ok_at` 是否在推进**，不要看计数。

### 2. 补抓文章晚于事件入日报，是正常时序

断档期文章在恢复后才入库、才分析。若当日日报在断档前后已生成，这些文章进的是次日的池子，不是"日报漏了"。

### 3. `blocked` 不等于丢失

分析管线会按相关度拦截低相关文章，`processing_state='blocked'` 是设计内行为。验收"是否全部处理完"时，`analyzed + blocked = 总数` 即通过。

## 结论怎么表述才诚实

| 想说的话 | 只有满足这些条件才能说 |
|---|---|
| "全部补回来了" | 逐源 `new_count >= 断档期发布数`，且各源发布数 ≤ feed 窗口 |
| "窗口内全部拿到" | 恢复首抓的 `new_count` 满窗且全是新条目 |
| "零永久丢失" | 每个源都做过源头对照，且发布数 ≤ 窗口 |

达不到最后一条时，如实说"未发现丢失"并给出理论上限，不要升级成"零丢失"。

## 改进方向（未实施，需评估）

对高频源（断档期单源发布量超过 feed 窗口的源）考虑：

- 分页拉取（若源支持分页参数）
- 按 `last_ok_at` 做时间窗回溯（若源支持 `?after=` 类参数）

前提是源支持，需逐个评估，不能一概而论。
